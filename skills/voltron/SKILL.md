# Voltron

Voltron is **formed**, the way the lions join into one robot: in every status line and summary the verb is *form* (Turkish *oluşturmak*: "Voltron oluşturuyoruz", "Voltron oluşturuldu"). The Black Lion splits the job at hand into parts, each lion builds one part at the same time, and the Black Lion arranges for the parts to be joined into one working whole. Read [lions](references/lions.md) first, for who the lions are, choosing lions and models, the Black Lion's quota, the plan format, running and reading results; in a repository checkout it is `../cogitors/references/lions.md`.

## Form Voltron

1. **Split.** Read quota before planning. Break the current job into independent parts, one per lion, at most five. Give each part its own `owns` paths and a handoff contract: the named outputs the lion returns and the checks that prove the part done, each with the command to run. Write checks specific to the task, not roles ("be a careful developer"). State what does not count as done: a partial solution, a fix for a special case only, a reduction to another unverified claim, or a best-attempt summary. Tell a lion not to stop early only together with such a check as its gate. When parts meet at an interface, make sure the shared scaffold is in the working tree before dispatch. Every lion starts from the working tree as it is.
2. **Match lions to parts.** Pick the CLI or account by quota first, using capability only to rule out lions that cannot do the part. Then choose its model and effort from the live list for the part's size and risk. Follow any ordered `routing` fallback list as described in the shared reference.
3. **Announce.** Show the Black Lion's estimated management share and remaining quota in the plan line, with any handoff for joining and verification. Start right away on an explicit `/voltron` or request to form Voltron. For a proposal, log the user's answer with `cogitor.py proposal --kind voltron --answer ANSWER` and start only after a yes to the plan, including the lions, accounts, access and call ceiling. Say "Let's form Voltron!" in the user's language (Turkish "Voltron oluşturuyoruz!"). Show each lion's part and paths, and its dispatch line.
4. **Run** a `parts` plan with `--access edit`, or `review` when every part only reads (for example a review split by area).
5. **Join.** Follow the plan's assignment for joining and verification. Start joining a part only when its named outputs and checks are back. Handle definite quota errors as described in the shared reference. A finding blocks a part only when evidence (a failing test or command, a counterexample, a reproducible error) shows it breaks the part's checks or contract; log the rest as non-blocking. Use diffs from successful lions with changes and get approval for any `outside_owns` change. Apply the diffs one by one, resolve conflicts, then run the project's own checks and fix what the joining broke. This step is done when every part is applied or set aside with a reason and the checks pass, or their failures are named.
6. **Report** to the user in their language: what each lion built, what you changed while joining, the check results, and any part left undone. Agreement among lions of one model family is not verification; for a result that matters, at least one check comes from another family or a machine-checkable step. Then clean the run.
